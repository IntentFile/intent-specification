# A declared reopen: a retired target returns its source

- **Status:** draft
- **Issue:** https://github.com/eclipse-dirigible/dirigible/issues/6868

## Why

Two rules already in the language leave a gap between them.

An event-driven create-from is **at-most-once**, and [a retired target stops blocking its
source](./0024-supersede-a-retired-target.md): a target whose status is classified `cancelled` or
`void` no longer satisfies the guard, so the source may produce a replacement. That made "void and
reissue" expressible.

A create-from may also declare a **completion hook** - the status the SOURCE moves to once the target
exists (a proforma becomes INVOICED). It exists precisely so the guard-claimed source stops matching
its own trigger.

Put the two together and the door is unlocked with nobody able to knock:

```yaml
generates:
  - name: invoice-from-proforma
    from: Proforma
    to: Invoice
    event: { onTransition: Proforma, when: "Status == APPROVED" }
    map: { Proforma: id }
    sourceStatus: INVOICED
```

1. The proforma is approved; the invoice is minted; the completion hook moves the proforma to INVOICED.
2. The invoice is wrong and is voided. It is retired, so it stops blocking - the proforma's one slot is
   **free**.
3. Nothing can refill it. The proforma stands at INVOICED, and a lifecycle graph declares no edge from
   INVOICED back to APPROVED, so the proforma never transitions through APPROVED again and no qualifying
   event is ever published. The trigger cannot fire.

Where the create-from also keeps a button the author can click it. An **event-only** rule - the shape
the event axis was introduced for - has no reissue path at all, and nothing says so: the model reads as
automatic and stops being automatic exactly once.

## What this adds

The completion hook's **inverse**, on the same rule: where the source returns when the target it
produced is retired.

```yaml
generates:
  - name: invoice-from-proforma
    from: Proforma
    to: Invoice
    event: { onTransition: Proforma, when: "Status == APPROVED" }
    map: { Proforma: id }
    sourceStatus: INVOICED           # forward: the proforma is done once the invoice exists
    sourceStatusOnRetire: APPROVED   # back: voiding the invoice returns it - and the trigger re-fires
```

Retiring the invoice returns the proforma to APPROVED. That is a real transition of the proforma, so it
is announced on the source's transition channel like any other, the ordinary trigger re-fires, the
at-most-once guard steps over the retired invoice, and the replacement is minted. **The reissue is the
ordinary path**, assembled from rules that were already there - not a second creation route with its own
semantics.

Nothing new says what "retired" means: it is the same `stage:` classification the guard reads, asked
from the other end. The guard asks whether the target that exists is retired; the reopen asks whether
the transition that just happened is what retired it.

Returning to a status a **person** must act on is the way to make a reissue reviewable rather than
immediate: return the proforma to DRAFT and the trigger, which qualifies on APPROVED, does not fire
until somebody approves it again. The reopen only announces the transition; the trigger's own guard
decides whether anything follows.

## Expected behaviour

> **Normative.**
> A create-from MAY declare `sourceStatusOnRetire`, the status its SOURCE returns to when a target
> generated by that rule becomes retired.
> It MUST be rejected unless the rule also declares `sourceStatus`, of which it is the inverse, and it
> MUST name a different status - a write that leaves the status where it stands is not a transition and
> announces nothing.
> It MUST be rejected on an appending rule: such a rule keeps no at-most-once guard, so no slot is ever
> consumed for a retired target to free.
> It MUST be rejected when the target's retirement cannot be recognised where the rule is declared:
> when the target carries no `function: EntityStatus` relation, when its nomenclature carries no
> `cancelled` or `void` `stage:` classification, or when the target belongs to another model (its
> nomenclature is seeded there).
> When a target generated by the rule becomes retired, the source still stands at the rule's
> `sourceStatus`, and no target of that source still satisfies the at-most-once guard, the source MUST be
> moved to `sourceStatusOnRetire`, and that move MUST be announced on the source's transition channel -
> the same channel every other routed status write uses, so a trigger bound to it observes the reopen
> exactly as it observes a transition somebody performed. When a target of that source still satisfies
> the guard, nothing MUST happen: a creation would hand that target back rather than mint a replacement,
> so returning the source would leave it re-opened with a target that still counts against it.
> Only the status MUST be written; no other value of the source may change, and the retired target MUST
> be left exactly as it is.
> When the source does NOT stand at that status, nothing MUST happen.
> The move is a transition, so where the source declares a lifecycle graph the edge from `sourceStatus`
> to `sourceStatusOnRetire` MUST be declared - that is where the source stands when the retirement
> arrives.
> A file that declares no `sourceStatusOnRetire` MUST regenerate byte-identical output.

## Edge rules

- **Idempotent by state, not by a marker.** Two conditions carry it: the source stands at
  `sourceStatus`, and no target of it still counts. The second is what closes redelivery - delivery of a
  retirement is at-least-once, so it can arrive again after the replacement exists, and by then the
  source is standing at `sourceStatus` once more. The same condition disposes of the retirement of an
  older target from a previous cycle.
- **A source that moved on is not overruled.** If the source has since travelled further down its own
  lifecycle, the reopen does not drag it back - that decision is no longer this rule's to make.
- **The reissue is not guaranteed to be immediate, and that is the point.** The reopen publishes a
  transition; whether a document follows is decided by the trigger's own `when:`. Returning to a status
  the trigger qualifies on reissues at once; returning to an earlier one waits for a person.
- **Several rules on one source** each return it to their own status, and each acts only from their own
  `sourceStatus`, so they cannot fight over it. Two rules sharing a target *and* a back-reference are
  already refused for the guard's sake.
- **A retired target is never re-pointed.** Both documents keep their back-reference and stay readable;
  this rule adds no cleanup of the retired one.

## Alternatives considered

- **Let the target's retirement re-deliver the source's qualifying event.** The void is the business
  moment that reopens the slot, so the target's lifecycle could republish the source's transition. This
  fabricates a transition that did not happen - the source is standing at the post-generation status, so
  the republished event would not even match the trigger's guard unless the guard were bypassed - and it
  re-fires every other consumer of that channel for a move nobody made.
- **Document the combination and warn about it.** Have a generator report that an event-only rule with a
  completion hook has no reissue path, and require a button. Honest, and cheap, but it leaves the
  automation inexpressible: the answer to "the document was voided, raise the next one" becomes "click
  here".
- **A cardinality.** An appending rule would produce the replacement and also produce a document on
  every later qualifying event. Cardinality answers how many targets a source may have; this answers
  where the source stands.
